# HacKU 2026 酒店选择智能体开发依据

本文面向 StayPilot 的开发、演示与答辩。依据是用户提供的官方参赛手册、官方赛题文件，以及酒店监控经验 PDF。核心判断是：赛题一要求证明一个人如何把一项花钱决策交给智能体、规则如何实际限制它，以及交易或失败发生后谁持有什么订单和资金。搜索更多酒店、接更多工具本身不能替代这些证据。

以下明确区分**官方要求**、**本项目对要求的理解**与**当前可核验事实**。建议的开发优先级不是官方额外评分规则，不能保证获奖。修改功能时，应同步修改这份依据及验收表。

版本日期：2026-10-04。参赛方向：FinTech 第一题 Give a Machine a Wallet – Agentic Commerce，由 HKT 赞助。

## 2 两轮总体评分

展览轮与入围后的 Pitch 轮分别是 30 分，均由六项各 5 分组成。手册没有规定两轮分数如何相加，因此不自行计算总分或保证某个名次。技术评委在展览轮选出 Top 8，再进入 Pitch。

| 展览轮标准 | 分值 | 酒店 Demo 应体现的证据 | 当前缺口或注意点 |
| --- | ---: | --- | --- |
| Problem & User Needs | 5 | 特定用户为什么要在预算内同时判断通勤、评论、取消与价格变化；真实经历或用户验证 | 用户提供的需求和参考文是问题依据，尚没有真人访谈/受试者实验，不能声称已验证市场规模 |
| Solution & Human-Centered Design | 5 | 每一步一个清晰界面；用户看懂自己让步了什么；硬底线与降级分开；能撤销 | 六步流程与移动端需要实际页面核验，不能只放流程图 |
| Technical Implementation | 5 | 后端交易守卫、报价重核、幂等、取消补偿、退款账本；实际网页/API 操作 | 仿真交易与真实只读接口必须分开说明；模型辅助模式尚未做线上模型验收 |
| Prototype & Demonstration | 5 | 一条稳定成功路径、一条实际阻断路径；订单、金额、截图和记录能对应 | 录制材料应跟随最新实现，不能拿旧视频证明新界面 |
| Innovation & Creativity | 5 | 把个人取舍转成可执行授权；按评论风险与取消价值做持续决策，处理换订风险 | “AI 查价”和“降价提醒”已有实例，不能把它们单独宣称为首创 |
| Practicality & Impact | 5 | 真实平台验证、可行合作与支付路线、明确成本和失败边界 | 最终含税报价、生产订单及退款权限仍需合作开通；自动化回放耗时不等于用户节省时间 |

| Pitch 轮标准 | 分值 | 答辩应回答 |
| --- | ---: | --- |
| Problem Framing & Relevance | 5 | 谁在什么行程里遇到什么取舍，为什么一次排序解决不了 |
| Market / Competitive Understanding | 5 | OTA 筛选、比价工具、价格监控 Agent 各解决什么；我们增加哪些授权和交易责任 |
| Solution Effectiveness & Value Proposition | 5 | 用一个完整例子说明少了哪些持续判断；价格节省与人力节省分别有什么证据 |
| Innovation & Differentiation | 5 | 个人评论底线、逐级降级、先订后退与失败冻结如何结合 |
| Pitch Structure & Delivery | 5 | 三分钟以内完成问题、规则、成功、阻断、证据和边界，避免逐项念功能 |
| Impact, Feasibility & Future Vision | 5 | 哪些已运行，哪些需商户审批，如何试点，以及数据和资金风险如何收敛 |

对开发的理解：六项同权，不能为了功能数量牺牲用户流程和演示稳定性。新工具只有在补齐核验字段或交易能力时才优先接入。

## 3 HKT 专项评分与支付现实性

| 官方标准 | 权重 | 对应开发要求 |
| --- | ---: | --- |
| Problem–solution fit | 25% | 定义住宿消费委托；完整成交与实际停止都能演示 |
| Technical execution and working prototype | 25% | 可运行代码、清晰架构、规则判断和失败恢复 |
| Security and trust design | 15% | 授权、同意、审计、失败处理；评论不能改变权限 |
| User experience and desirability | 20% | 看懂当前步骤、预算、降级代价、取消选择；普通用户能操作 |
| Feasibility of integration with any payment means | 15% | 说明实际拟接入的支付路径及依赖，不能仅画一个钱包图标 |

官方评价支付通道提案的现实性，列举 Mastercard、UnionPay、FPS 等例子，并没有要求采用某一家。我们首版选择平台内人民币结算，不同时处理汇率与积分估值。当前仿真钱包是规则验证账本，不是银行卡、预付金融账户或真实支付接入。

拟接入真实成交的顺序：商户获得最终含税、房型、人数、餐食、取消政策绑定的报价 → 本机审核用户授权与资金限制 → 商户官方下单/支付能力或平台结算交接 → 查询确认订单 → 用官方取消/退款能力查询实际状态。成交接口、测试资金方案、支付身份、退款回调、幂等和报价有效期必须由商户文档确认。当前 FlyAI 搜索成功不证明这些能力已开通；普通消费者登录也不产生 API 订单权限。

费用、手续费、返现、积分价值只能使用实际观察并标注时间的数值。未知时显示未知，不能拿行业常识填出一个百分比，也不能用搜索展示价推导最终含税总价。

HKT 专项奖还要求团队声明对应其赞助赛题。SenseTime Raccoon 奖要求真实使用该平台并说明贡献；没有使用证据时不填写使用声明。官方演讲翻译不是评分文件，未从其中推断新的评分权重。

## 4 赛题一的不可替代证据

| 编号 | 官方范围或 Evidence 要求 | 本项目应怎样证明 |
| --- | --- | --- |
| O1 | 一项 spending decision 与一个 delegating party | 用户授权单：一次固定日期住宿选择，单一用户委托 |
| O2 | 定义可做、不可做，以及额度/授权/期限/规则/撤销如何 enforced | 后端提交时审核；前端显示的限制必须对应实际拦截规则 |
| O3 | 一笔完整端到端交易，至少一个 stopped case | 实际仿真商户网页预订、资金扣除、确认订单；税费超额等导致拒绝并无扣款 |
| O4 | 先展示允许做什么的日志，再展示停止 | 同一证据链里能看到授权版本、报价观察、结算复核、拒绝原因和钱包结果 |
| O5 | 与 manual route 比较步骤、时间、成本 | 同种子市场路线记录；明确当前是自动化传统路线回放，真人耗时验证另行进行 |
| O6 | 用户可理解的决策规则 | 先硬底线、再降级档位、评论风险、含税价格与通勤；展示各候选的取舍和非首选原因 |
| O7 | rate、fee、cashback、points 等须为 observed 且 timestamped | 真实搜索及网页观察留时间；仿真种子费率明确标为测试数据，不宣称市场价格 |

对演示的理解：赛题没有指定必须使用某一支付方式、某一种 Agent 框架或所有 Potential directions。仿真交易能证明当前测试商户内规则的执行，但不能证明真实支付成功；官方文件也没有承诺纯仿真必然达到高分。我们应同时展示真实查询证据、仿真交易闭环和真实成交的未完成权限，而不混为一谈。

## 5 用户流程和每一步必须看见的内容

| 界面 | 用户操作或智能体动作 | 输出与禁止事项 |
| --- | --- | --- |
| 01 行程计划 | 选住宿附近目的地、入住/退房、人数/房间、房型、住宿总预算 | 保存的是草稿；首版单主要目的地，城市列表不证明多个景点可达 |
| 02 取舍与授权 | 确认评分底线、步行/地铁、开业、窗型、评论雷点、降级顺序、期限、取消权限 | 明确确认后才生效；默认不可取消禁止；额度不会给钱包充值 |
| 03 初筛与评论 | 平台 A 初筛 3—5 家意向，读取详情和正反评论 | 展示为什么入选、为何淘汰、来源/日期/样本量；列表没读评论不能直接买 |
| 04 三平台比价 | 同酒店同条件核价，发现其他平台候选 | 含税总价、餐食、人数、取消政策分别核验；评分原尺度保留；过期报价不视作现价 |
| 05 预订或阻断 | 合格报价提交前重核；商户确认或拒绝 | 区分排序首选、提交成功与订单确认；失败不能扣款或伪造订单 |
| 06 订后监控 | 可取消订单继续查更优酒店；不可取消则锁定 | 展示新旧单、退款占款、到账与失败冻结；停止监控不会自动取消住宿 |

页面的进度由运行阶段、已读候选、排序记录及真实订单状态决定，不能因为任意观察计数大于零，就把所有步骤涂成完成。用户可以查看后续界面，但缺数据时显示等待，不能预填虚假结论。

## 6 选择与换订规则

预算不足时只按预先确认的顺序累计放宽：步行 → 地铁直达、近年开业 → 不限年份、期望评分 → 已确认最低分、有窗优先 → 明确接受无窗。用户可以调整顺序。有窗为硬底线时，即使无窗出现在降级列表也不能放宽；窗型缺失时不能自行认定合格。不能将用户“评分不高于”口语模糊表达直接解释为降低品质，确认界面采用明确的“最低可接受评分”。

评论风险采用已读取样本的问题比例乘用户权重并累加；属于雷点的明确问题直接排除。比例是已读取样本的统计，尤其定向筛选差评时，不代表全部住客的发生率。显示近期正面反证、老评论、样本不足、可能重复和冲突。开业与翻新分别记录；评分尺度不同不代表相同分数有相同口碑含义。

同档位先比较个人相关差评风险，再比较含税总价和通勤。高评分不覆盖卫生雷点，最低价不覆盖取消权限，模型输出不修改预算或规则。

可取消订单的换订需：新酒店档位和风险不更差；净省同时达到 50 元及原价 5%（可编辑）；旧单可全额退、新单有补偿取消窗口；旧单免费取消截止前至少留 1 仿真小时；余额和临时占款额度足够。先确认新单，后退旧单。退款到账前继续占款，并暂停重复换订。旧单取消失败要补偿取消新单；补偿、退款或状态不确定时冻结，展示实际账本。

首次预订截止前必须取得确认订单。截止前 1 仿真分钟做最后核验；无解时停止购买，最多三套条件组合，预算差额基于已见含税报价，超出授权必须再次确认。首版不拆分酒店入住。

## 7 可核验记录与可信度边界

每次关键动作记录：授权版本及边界、观察时间与真实执行时间、报价绑定条件、评论证据、命中的规则、候选排序、提交或阻断、商户订单及退款状态、网页截图。

“为什么这样选”应引用当时记录的字段与规则，而不是事后生成没有来源的解释。展示的是供用户核对的决策依据，不要求披露模型内部思维过程。历史证据不得覆盖成当前成交事实。

当前仿真日志的哈希链可检测记录内容、顺序与链条是否改变，但若操作者能重写整条链且没有外部保存的可信根，单靠哈希链不能防止其整体伪造。答辩不能宣称已经实现第三方不可抵赖、银行对账或商户签名。真实只读监控目前是 SQLite 历史与规则事件，也不宣称已接入商户财务对账。

## 8 参考经验和竞争位置

酒店监控 PDF 提供了三个有用做法：先筛少量意向，保存 baseline/lastSnapshot；比较已观察的价格变化；用阈值判断是否值得行动。我们保留历史与阈值，但按用户要求把结论和操作放在网页，不接飞书发消息。作者文中的价格和节省案例不作为我们的实测数据。

| 现有路线 | 解决什么 | 本项目增加的部分 |
| --- | --- | --- |
| OTA 搜索与筛选 | 当前平台列表与商品详情 | 提前确认降级顺序、跨平台证据与授权内持续执行 |
| 比价或价格监控 | 某一酒店价格差/变化提醒 | 把评论雷点、取消资格和换订占款一起作为行动条件 |
| PDF 中的监控 Agent | 定时查询、状态记录、阈值提醒 | 在网页内执行测试预订、阻断、补偿和退款冻结 |

这是功能位置比较，不是对所有竞品做完测试的结论；不能声称所有 OTA 或 Agent 都没有这些能力。参考 PDF 末页说当时 RollingGo 以查价为主；当前仓库文档已描述更多 OAuth 交易工具，实际账户权限仍须联调。第三方教程不能替代商户最新 schema。

## 9 当前实现与下一轮优先级

已实现：三平台、20 家测试酒店、实际网页浏览、后端交易守卫、订单退款账本、截止替代方案、截图与日志；六步独立界面与窗型条件；FlyAI 真实搜索、一个酒店的历史网页评论/取消条款、只读监控；本机四工具 MCP 及 Booking 官方工具发现连接器。新增设施底线、开业/翻新口径、首选与三个备选、提前条件组合，Step Plan偏好/评论提取及高德位置/通勤查询已实测；详细证据见 [个人流程更新](personal-workflow-update.md)。

已验证的真实接口只读，搜索价不等于含税总价，真实成交始终阻断。Booking 尚无合作凭证。RollingGo 中国端点已匿名初始化探测返回 HTTP 401，说明仍需对应 Key，不代表鉴权或酒店查询成功。Expedia/Agoda 只有官方流程研究，不宣称已接通。商户数据不是预知未来的市场。

下一轮顺序：

1. 六步流程与窗型守卫已验收：38项单元、9项仿真浏览、6项截止边界通过；独立浏览器也完成新界面的首订、换订与退款核对。
2. 视频已重录为180秒；Deck v2已逐页检查。交付源码应对应六步界面与真实只读功能，发布记录以Git为准。
3. 若能获得凭证，先补当前真实商户的绑定含税报价、取消条款与沙箱订单，优先于继续增加搜索平台数量。
4. 采集真人操作过程或访谈；没有证据前不写“省时 X%”或真实收益。保持当前回放基准的限制说明。

## 10 三分钟演示和交付门槛

建议分配：0:00–0:25 特定用户与复杂取舍；0:25–0:55 行程、硬底线、降级、取消权限与测试钱包；0:55–1:35 浏览证据、跨平台排序、确认订单；1:35–2:10 降价换订和退款占款；2:10–2:40 税费超额或撤销后的实际阻断；2:40–3:00 真实飞猪查询、未开通交易边界及可行接入路径。

官方提交截止是 2026-10-04 13:00 香港时间（与上海同为 UTC+8），要求此前提交代码；提交材料需公开可见：GitHub/GitLab 链接、在线 Demo 或 3 分钟录屏、Pitch Deck。海报可选。展览及入围演讲至少一名代表到场，报名与选赛道也有前置要求；软件工作不能证明团队已完成这些事务。

提交前逐项核验：代码版本一致；录屏能公开打开且不是纯概念动画；Deck 链接与截图对应；成功和阻断都实际执行；真实与仿真标注清楚；密钥无泄露；原始官方资料不随公开包分发；传统回放与真人实验区分；支付接入边界如实披露。仓库公开、提交表单、合作申请或真实购买只在相应授权范围内执行，不用本地文件存在来宣称已经提交。

## 11 官方原文定位

赛题文件的 FinTech 第一题：Scope requirement 中的 spending decision、delegating party、actually enforced、complete transaction、stopped；Evidence 中的 permissions log、manual route、decision rule、observed and timestamped。手册第 7 节分别列出 Exhibition 30 Marks、Pitching Round 30 Marks 与 HKT 五项权重；第 5 节列出 Required Deliverables 和 Code Freeze。需要争议判断时回到这些原文，而不是从本手册的优先级建议反推官方规定。
